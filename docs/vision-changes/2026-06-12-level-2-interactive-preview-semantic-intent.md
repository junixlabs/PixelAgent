# Vision Change Proposal — Level 2: Interactive Preview, Flow Links, Semantic Intent, Consistency Validator

**Date:** 2026-06-12
**Status:** Approved by maintainer 2026-06-12
**Affects:** VISION.md "Explicit non-goals" (one line amended), `packages/dsl-spec/SPEC.md` (params only, no new commands), roadmap ordering.

---

## Motivation

Three findings from live agent-driven usage (Claude Fable 5 via the MCP server, 2026-06-12):

1. **The interactive preview already exists and is discarded.** `dsl-to-html.ts` emits real CSS `:hover` selectors from `STATE`, real `<button>`/`<input>` elements. The renderer screenshots one frame and throws the living HTML away. PNG-only output is an output-format decision, not an architecture constraint.
2. **PNG previews cannot express flows.** Reviewing a multi-screen UX (login → home) requires linking screens. Figma prototypes prove static link maps are a *preview* concern, not app logic.
3. **Codegen output is not production-ready.** `TEXT` → `<span>`, `IMAGE` → `<div data-src>`, no headings, no links, no alt text. The DSL captures geometry but not intent, so synthesized code cannot be semantic, accessible, or SEO-capable — failing the North Star's "production-ready" clause.

## Proposed changes

### 1. Interactive HTML preview (no DSL change)

- `POST /preview` accepts `format: "png" | "html"` (default `png`, unchanged).
- MCP `outPath` accepts `.html` in addition to `.png`.
- The HTML output is the existing internal document, plus a small dev overlay: clicking an element shows its id + DSL line (supersedes the Phase-3 alpha-channel ID-buffer plan with plain DOM).
- **Hard boundary:** a click in preview may only (a) reveal a visual state, (b) navigate to another screen. No handlers, no data, no validation, no conditions. The preview HTML is throwaway; DSL stays the only source of truth.

### 2. Flow links (one param, no new command)

- `goto:<screen-id>` param on `BUTTON`, `TEXT`, `ICON`, `IMAGE`.
- `POST /preview` accepts `{ screens: { "<id>": "<dsl>", ... }, entry: "<id>" }` and renders a navigable bundle (HTML) or per-screen PNGs. Stateless: the full bundle travels in each request.

### 3. Semantic intent params (params only, renderer-neutral)

| Param | On | Codegen effect | Renderer effect |
|---|---|---|---|
| `level:h1..h6` | TEXT | emits `<h1>`–`<h6>` | none (size/weight stay explicit) |
| `alt:"..."` | IMAGE | emits `alt` attr; `<img>` replaces `<div data-src>` | none |
| `href:"..."` | BUTTON, TEXT, IMAGE | emits `<a>` wrapper | none |
| `role:nav\|header\|main\|section\|aside\|footer` | LAYER, STACK, GRID | emits semantic container tag | none |

Still 15 commands. Renderer pixels unchanged — intent is invisible to the bitmap, load-bearing for codegen.

### 4. Consistency validator (promoted from Phase-2 backlog)

Deterministic lint on the AST, output as `ValidationWarning[]` with line numbers: token-coverage (raw hex where a token exists), spacing-rhythm drift, hover-state coverage on interactive elements, **contrast** (first rule: ghost variant on `theme:dark` — found live), existing tap-target rule. Rationale: the AST is the agent's native review surface; deterministic lint catches what neither human eyes nor vision models measure reliably.

### 5. Renderer fix

`ghost` button variant on dark theme must inherit theme foreground color (currently near-invisible dark-on-dark).

### 6. Architectural Invariant #8 — No non-local effects

Codifies the founding property that makes patches safe and the DSL statically reasonable. Add to VISION.md "Architectural Invariants":

> **No non-local effects.** An element's rendered appearance is a pure function of its own declaration, the tokens it explicitly references, the screen theme, and its ancestor chain. No cascade, no specificity, no inheritance beyond documented defaults, no external styling — ever. Any future feature that introduces override-at-a-distance is rejected by this invariant.

Flow layout (STACK/GRID) is compatible: positions are renderer-computed but fully determined by the document alone.

### 7. Synthesis contract (anti-drift)

Synthesis is a one-way door; without a contract the .dsl rots into stale documentation the moment developers edit generated code. Adopt the schema-codegen pattern (protobuf/Prisma/OpenAPI):

1. **Header:** generated components carry `// GENERATED by PixelAgent from <name>.dsl — dsl-sha256:<hash> — do not edit; edit the DSL and regenerate.`
2. **Determinism:** same DSL → byte-identical output, so regeneration is always safe and diffs stay clean.
3. **Shell/wrapper boundary:** generated code is presentational only — TEXT content becomes props with DSL values as defaults, element ids become stable DOM ids for handler attachment; logic/data/state live in a developer-owned wrapper that regeneration never touches.
4. **Drift check:** a verify helper compares the embedded hash against the .dsl file (CI-friendly). Hand-edited output or un-regenerated DSL = detectable failure, not silent rot.
5. **Exit door:** deleting the header is the explicit act of taking manual ownership of a screen that has outgrown PXL.

Applies to build-order item 4 (semantic codegen) — designed in from the start, not retrofitted.

## VISION.md amendment

Non-goal line "Animation / transition support" stands. The line "Adding animations, transitions, or interactivity to DSL" in CLAUDE.md is clarified, not removed: **no interactivity is added to the DSL** (STATE predates this proposal); the change is that the renderer stops discarding the interactive artifact it already builds. Add changelog entry:

> **2026-06-12:** Level-2 scope: HTML preview output, `goto:` flow links, semantic intent params (`level`, `alt`, `href`, `role`), consistency validator. Click-in-preview limited to state-reveal and screen-jump. Still 15 commands.

## Feature Decision Filter check

1. Which of the 3 Problems? — Problem 3 (consistency/validator, semantic correctness) and Problem 1/2 (flows previewable and patchable before any code exists).
2. More like Lovable? — No: no logic, no data, no hosting; Figma-prototype-grade linking only.
3. Requires state/DB/backend? — No: screen bundles travel per-request, stateless.
4. Could a coding agent already do this? — Not without generating full code per screen, which is the cost/drift problem PixelAgent exists to remove.

## Build order (proposed Forge issues, in sequence)

1. HTML preview output (`format:"html"`, MCP `.html` outPath) + click→id overlay — smallest diff, biggest feel win.
2. Ghost-on-dark renderer fix + contrast lint rule (seed of validator).
3. `goto:` param + multi-screen bundle + HTML navigation.
4. Semantic params in spec/parser + semantic codegen (React first).
5. Remaining validator rules (token-coverage, spacing-rhythm, hover-coverage).
6. README repositioning (determinism-first) once 1–5 are dogfooded.
